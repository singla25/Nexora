# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A WordPress + WooCommerce site (full WP core is committed) with project-specific code in two places only:

- `wp-content/plugins/nexora/` — the custom plugin: front-end registration/login, profile dashboard, user connections, notifications, chat, and the multi-vendor **marketplace** (vendor accounts, products, imports, cart, orders, earnings).
- `wp-content/themes/nexora-theme/` — classic PHP theme with Elementor Pro integration and a sample-content installer (`inc/elementor`).

Everything else (WP core, WooCommerce, Elementor, Elementor Pro, ACF, other plugins, stock themes, Hostinger mu-plugins) is third-party; don't edit it. See [README.md](README.md) for the shortcode table, setup steps and feature list.

References: `docs/SPEC.md` is the source of truth for marketplace rules (accounts, products, imports, cart, orders, which order statuses count as earnings); `docs/TEST_PLAN.md` lists what each test file proves and the test-isolation rules. Older subsystem docs: `ARCHITECTURE.md`, `AJAX-API.md`, `AUTHENTICATION.md`, `DATABASE.md`, `THEME.md`, `DEVELOPMENT-WORKFLOW.md`, `TROUBLESHOOTING.md`, `CODE-REFERENCE.md`, `NEXORA-DEVELOPER-GUIDE.md`; consult them before re-deriving how a subsystem works.

No build step — plain PHP/CSS/JS, PHPCS for linting, and a WP-CLI test harness in `tests/`. Run and verify changes in the browser (site is served under `/nexora/`; `.htaccess` `RewriteBase` assumes that). `wp-config.php`, uploads and DB dumps are git-ignored.

## Commands

- Tests (WP-CLI, ~7 minutes for all) **run only on a scratch copy of the database**: `NX_TEST_DB=<scratch db> tests/run.sh`, or `... tests/run.sh tests/php/test-foo.php` for one file. The runner, `tests/bootstrap.php`, `tests/purge.php` and `tests/guard.sh` refuse (exit 3) to run on the database in `wp-config.php`; the only exception is `NX_ALLOW_LIVE_READONLY=1` for the few write-nothing tests listed in `tests/live-readonly.txt` (`tests/live-guard.php`). **Work test-first: follow the `tdd-workflow` skill (red, green, refactor) before building or fixing anything.** Test rules below.
- Coding standards (WPCS via PHPCS, must report nothing): `cd wp-content/plugins/nexora && composer install && vendor/bin/phpcs` (auto-fix with `vendor/bin/phpcbf`). Composer is installed per developer (`php composer.phar`); `vendor/` is git-ignored and never deployed. Plugin developer notes: `wp-content/plugins/nexora/README.md`.
- Strings: wrap every user-facing PHP/template string in `__()` / `esc_html__()` / `esc_html_e()` with the `nexora` domain, then regenerate `languages/nexora.pot` (`wp i18n make-pot wp-content/plugins/nexora wp-content/plugins/nexora/languages/nexora.pot --slug=nexora --domain=nexora --exclude=vendor,assets/lib`); `test-i18n.php` fails on untranslated text or a stale `.pot`.
- Syntax-check: `php -l file.php`, `node --check file.js`, or the whole plugin/theme: `find wp-content/plugins/nexora wp-content/themes/nexora-theme -name '*.php' -print0 | xargs -0 -n1 php -l | grep -v '^No syntax errors'`
- Flush rewrites after touching rules: *Settings → Permalinks → Save* (or `wp rewrite flush`).
- Project skills in `.claude/skills/` (`nexora-add-module`, `nexora-add-ajax-endpoint`, `nexora-db-table`, `nexora-elementor-page`, `nexora-release-assets`, `nexora-data-model`, `nexora-settings-option`, `nexora-auth-flow`, `nexora-frontend-style`, `raise-pr`, `verify-like-a-user`) cover the common change types; run `nexora-release-assets` before finishing any plugin/theme change. `raise-pr` confirms before each outward-facing step.

## Tests: they share the dev site's database

The suite runs inside WordPress against the real DB, so a careless test can destroy the site's saved settings or its real Marketplace Item (real orders point at it). Rules, enforced by `test-isolation-lint.php`:

- **Settings are scoped, never saved/restored by hand.** `tests/bootstrap.php` puts every test on known default settings (`nx_test_default_settings()`); a test needs other values via `nx_test_options( [ name => value ] )` (null = absent) or `nx_test_options_keep()` (edit it yourself, it is restored). Restores are raw SQL, run from `nx_test_finish()` and a shutdown hook (also after a fatal), and bypass sanitizers. A new Nexora option must be added to `nx_test_default_settings()`, `tests/tools/guard-state.php` and the lint's list.
- **A test only deletes what it created** (`nx_test_user/vendor/product/order`, tracked ids, `nx_test_*`/`nxtest_*`/`nx_iso_*` names). Anything touching the Marketplace Item calls `nx_test_marketplace_item_scope()` (works on a scratch item). Rate-limit counters, API caches and locks are set aside and restored by the harness.
- **Orders:** `nx_test_order( $buyer, [ [ $product_id, $qty ] ], [ 'payment' => 'bacs|cod', 'status' => … ] )` builds a real order through the cart → `WC_Checkout::create_order()` → `woocommerce_checkout_order_processed` pipeline.
- **Anything that changes site options should run on a scratch copy of the database:** create a DB, load `mysqldump` of the live one, then `NX_TEST_DB=<db> NX_SKIP_LIVE=1 tests/run.sh` (every `wp` call, children included, follows it). `NX_SKIP_LIVE=1` skips tests that make real web requests (`curl_init`; the web server only sees the live DB). `tests/guard.sh` (run with `bash`, also with `NX_TEST_DB`) sets hostile settings, runs everything and checks the originals come back byte for byte. `NX_TEST_KEEP_SETTINGS=1` turns the default-settings scoping off.
- Golden snapshots: `tests/php/test-golden-output.php` pins the exact markup of every screen (`tests/golden/`). A refactor must keep them identical; if markup changes on purpose, regenerate with `NX_UPDATE_GOLDEN=1 tests/run.sh tests/php/test-golden-output.php`, then review the diff — it also rewrites `auth-buttons-member` / `form-login-member` with noise, so `git checkout` those two. `test-static-namespaces.php` fails on any unresolved class reference in `src/`.
- Direct `wp_update_post` / `wp_delete_post` on products and vendor applications is refused by `Core\Post_Guard` on purpose; write through the Service/Repository classes, or `$wpdb->update` to set up a state in a test.

## Architecture

- `nexora.php` is only constants + the PSR-4 autoloader (`src/Core/Autoloader.php`, namespace `Nexora\` -> `src/`) + the activation hook + `Nexora\Core\Plugin::boot()`. **A new module is one class under `src/<Module>/` plus a `new` line in `Plugin::boot()`** (no `require`). Old global class names (`NEXORA_Notification`, `NEXORA_CHAT_DB`, ...) still resolve through `src/Core/legacy-aliases.php`.
- Social core: `Core` (Plugin, Assets, Access_Control, Urls, View), `Http` (Ajax registrar + guard, Member_Ajax, Rate_Limiter), `Auth`, `Profile`, `Connections`, `Notifications`, `Content`, `Chat`, `Admin`, `PostTypes`, `Shortcodes`, `Database`. Markup lives in `templates/` (rendered with `Core\View::render()`; prepare data in the class, escape in the template); CSS/JS in `assets/`.
- Access control (`Core\Access_Control`): non-admins are bounced from `wp-admin`/`wp-login.php` to their profile; logged-out visitors go to `/login-page`; AJAX/REST/cron/`admin-post.php` are exempt. Page paths come from `Core\Urls`.
- AJAX: register with `Http\Ajax::register('name', $callback, $guest = false)` which creates `wp_ajax_nexora_name` and keeps the old un-prefixed `wp_ajax_name` as a deprecated alias. Member handlers extend `Http\Member_Ajax` and start with `$this->member()` (nonce + login + profile). Vendor/order handlers extend `Vendors\Vendor_Ajax`: `seller()` = approved vendors only, `earnings_viewer()` = approved + suspended (read-only history); the vendor always comes from the logged-in user, never the request. Rate-limit abusable actions with `Http\Rate_Limiter::hit()` (buckets in `Rate_Limiter::defaults()`); `test-endpoint-matrix.php` lists every action and fails on an unlisted one.
- Data model: CPTs `nexora_customer` (a customer's profile), `nexora_seller` (a member who registered directly as a seller; it is their profile too), `nexora_cust_seller` (the business details of a customer who became a seller), `user_connections`, `user_content`, plus `nexora_product`, `nexora_import_log`, `nexora_api_conn`; custom tables for notifications and chat, synced by `Database\Migrations` (edit the repository's `create_table()` `dbDelta` SQL and bump `DB_VERSION`). `uninstall.php` deletes data only if the "Delete data on uninstall" setting is on (`Database\Uninstaller`, which also lists the options). `/profile-page/<username>` is a rewrite rule; pages `login-page`, `registration-page`, `profile-page` must exist (Appearance → Sample Content creates them).
- **Marketplace layers** (each reads like a pipeline, read `docs/SPEC.md` for the rules):
  - `Accounts\Account_Types` — seller status (none → pending → approved/rejected → suspended) in user meta; three roles (core `subscriber` shown as Customer, `nexora_seller`, `nexora_customer_seller`, each `read` only). **Never ask for a role slug:** `has_seller_record()` = any status, `can_sell()` = approved. The role changes only on approval and when a seller record is deleted; suspension keeps it. `Core\Post_Types` is the one place that names the record types (`profiles()`, `sellers()`); `Accounts\Links::link()` is the one method that writes `customer_post_id` / `seller_post_id` / `_profile_id` / `_seller_post_id` / `_vendor_id`; `Accounts\Migration` (`wp nexora migrate-accounts [--dry-run]`) converted the pre-7a data. `tabs_for()` decides which profile tabs a member sees, `Profile\Page::BUILT_TABS` which exist. `Vendors\*` = application, admin approve/reject/suspend, one Repository/Service for both seller record types; a rejected record is kept and can be re-applied on.
  - `Products\*` — `Validator` is the one rule set used by the manual form, CSV import and API import; `Service`/`Repository` write, `Listing`/`Presenter` read. `Imports\*` — plan (dry run, nothing written) → one-time token bound to member, source and the "How many products" count → apply. API fetching is only in `Imports\Api_Source` behind `Imports\Url_Guard` (https, public addresses, DNS pinning, no redirects, size/time caps); formats: Nexora, DummyJSON adapter, Fake Store adapter; keys are encrypted (`Core\Secrets`) and never shown back.
  - `Marketplace\*` — the cart. Every purchase is one hidden WooCommerce product (`Marketplace_Item`); a cart line stores only `nexora_product_id`, and `Cart_Rules` (the single set of buy rules) plus `Cart_Bridge` re-read name, price, vendor and stock from the product post on every cart load and at checkout. Nothing the browser sends is a price.
  - `Orders\*` — `Placement` runs on both checkout paths (classic `woocommerce_checkout_order_processed`, blocks `woocommerce_store_api_checkout_order_processed`): re-checks, takes stock with one atomic `UPDATE … WHERE stock >= qty` (`Stock`), then freezes each line (product, name, SKU, price, qty, vendor, business name, commission rate/commission/earning) as hidden order-item meta — `Lines` is the only place that knows those keys. `Order_Events` and `Refunds` give stock back and reverse the vendor's share; they work from per-line counters (taken/given back/refunded) so every hook is idempotent. `Earnings` is never stored: it is read from the order's current status (**only Processing and Completed count**) and the frozen figures. `Commission` works in whole cents; rate option `nexora_commission_rate` (default 10). `Fulfilment` (Phase 9) lets an approved seller mark their own lines shipped on Processing/Completed orders (flag on the line in `Lines`; completes a Processing order when every non-refunded line is shipped; the buyer's shipping address is shown only while the seller has an unshipped line on a counted order). `Mailer` queues the order e-mails as a scheduled single event `nexora_send_mail` (templates in `templates/emails`; never throws, logs to the WooCommerce log) and writes the in-app notifications; `Low_Stock` is the threshold setting `nexora_low_stock_threshold` and the once-per-drop alert. `Reports` (Phase 8) is the read-only seller report and admin overview: sums of the frozen line figures only, 5-minute transient cache cleared on every order change, no buyer data; `Report_View` renders the Sales tab block, `Overview_Page` the admin page.
  - `Integrations\Woo_Routes` — closes WooCommerce's own front doors: Woo my-account and login/registration handlers, guest cart/checkout/Store API routes (401), guest checkout forced off. WooCommerce "Coming soon" mode hides cart and checkout from non-admins.
- Chat is `src/Chat/`; the third-party Better Messages plugin has been removed. `Integrations\Better_Messages` (and its `Plugin::boot()` line, alias and `tests/php/test-better-messages.php`) is leftover dead code.
- Theme: header/footer/404 can be overridden by Elementor Pro Theme Builder templates; theme markup is the fallback. Elementor sections are styled via `nxe-*` classes in `assets/css/elementor.css`. Dynamic values come from the plugin shortcodes `[nexora_stat]`, `[nexora_auth_buttons]` and theme shortcodes `[nxt_logo]`, `[nxt_setting]`. Sample pages are installed from Appearance → Sample Content and are idempotent.

## Gotchas

- **Profile privacy:** `Profile\Privacy` decides who gets private fields (email, phone, address, ID documents): only the owner, and only on the profile page. ID documents are **private files** (`Profile\Private_Documents` → `uploads/nexora-private/`, served only to owner/admin through `nexora_document`). Same spirit for orders: a vendor sees only their own lines and the shipping address (while the order still ships), never billing, email or phone.
- **reCAPTCHA is skipped only on a genuinely local site** (`Auth\Recaptcha::is_local`): `WP_ENVIRONMENT_TYPE=local` *and* the site's own hostname resolves to a private address, or the `nexora_skip_captcha` filter says so.
- **Git on this repo:** `.gitignore` ignores every plugin except `nexora`, but WordPress core and several third-party plugins are tracked (committed wholesale in `16cb22e5`), so an update in wp-admin shows up as hundreds of modified files — **never `git add -A` / `git add .`; add by explicit path**. `core.fileMode` is false locally (use `git -c core.fileMode=false add …`; executable bits are set with `git update-index --chmod=+x`). `origin` is public HTTPS GitHub; this session has no stored GitHub login (no credential helper, no `gh`), so pushing is the user's own step and you must never try to authenticate for them. **Never rewrite history or force-push unless asked.**
- Third-party `vendor/` folders (Elementor, ACF) are not in git, so those plugins fatal on activation from a fresh clone; install/update third-party plugins through wp-admin. Elementor Pro is a licensed product committed to a public repo.
- Header/Footer Theme Builder templates use Elementor Pro Nav Menu widgets bound to the menu slugs `nexora-main`, `nexora-footer-company`, `nexora-footer-legal`; those menus exist only after the sample-content installer has run.
- Home-page numbers (`[nexora_home]`, `[nexora_stat]`) come from `Shortcodes\Home::get_stats()`, cached in the `nexora_home_stats` transient and flushed by `save_post_user_*` hooks.
- CSS prefixes: plugin `nx-*` (tokens in `assets/css/tokens.css`), theme chrome `nxt-*` (`NXT_VERSION` in `nexora-theme/functions.php` busts theme asset caches), Elementor sections `nxe-*`.

## Conventions

- Bump `NEXORA_VERSION` in `nexora.php` (header and constant) whenever plugin PHP/CSS/JS ships, and regenerate the `.pot` if strings changed. Shared design tokens are enqueued via `Core\Assets::enqueue_tokens()`.
- Commit messages end with the `Co-Authored-By` line given by the harness; commits are made by explicit path; pushing is the user's call.
- Set `WP_DEBUG` to `true` in your local `wp-config.php` to surface notices.
